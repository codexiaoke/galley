# 写作

这份技能讲怎么写得好。正文里的标记怎么写见 `markup` 技能，知识块怎么拆见 `knowledge` 技能。

## 先有料，再动笔

读者一眼认出"机器写的"，多半不是因为某个词，而是因为整篇没有一样东西是这个站独有的：换掉站名，它放到哪个博客都成立。所以动笔前先问一句：**这篇里有什么是只有这里才有的？**

算数的料有这几种：

- **站长的经历和看法**：素材箱里的素材、`opinion` 观点块、站长在对话里亲口讲的经过和判断。
- **实际跑出来的结果**：你亲自运行过的命令、测出来的数字、复现出来的报错原文。
- **这个站自己项目里的东西**：源码、提交记录、配置、某次改动前后的差别。
- **自己设计的讲法**：一个具体好懂的例子，一段读者能亲手操作的演示，一次亲手做的验证。科普文主要靠这一种，见下面"写科普"一节。

官方文档、规范、别人的文章是用来**核实**的，不是用来**撑篇幅**的。如果一篇文章只是把文档换个说法复述一遍，就不要写——读者直接去看文档更好。这时改成 `propose_topic` 提题，在说明里写清楚还缺什么料；站长在对话里的话，直接问站长要。

**不要编经历。** "我当时……""我们踩过……"这种第一人称的经过，只能来自站长的素材或站长在对话里说过的话。从源码里看出来的事，写成"Galley 的实现里……"，不要包装成站长的回忆。站长没给的细节、数字、心情，一律不补。

### 和站长一起写

站长在对话里说"把我在做的这件事写写"时，不要拿到一句话就开写。先问三四个具体的问题，问到能写为止，比如：

- 当时具体卡在哪？报错、现象、数字是什么？
- 试过哪些路，哪条走不通，为什么？
- 最后怎么解决的？现在回头看，你怎么看这件事？

一次问一轮，不要甩一张问卷。站长原话里有意思的说法、口头的判断，尽量保留原样，不要改写成书面腔。问完先写一版短的给站长看，站长要展开再展开。

### 写科普

讲一个算法、一个原理、一个概念，知识本身谁都查得到，这个站能多给的是讲法。站里的 `二分查找：为什么敢跳过一半` 就是样子：不讲定义，用几个价格让读者自己看出"为什么能扔掉一半"。

- **只回答一个"为什么"。** 不写"X 是什么、有什么用、优缺点、应用场景"那种百科条目。挑一个读者真会卡住的点，比如"为什么二分查找要求有序""为什么哈希表查找是常数时间"，整篇只回答它。标题也就是这个问题的答案。
- **从一个具体例子进去，而不是从定义进去。** 一组数、一个价格、一段能跑的代码，读者先看到现象，再看到道理。例子要小到读者能在脑子里跟着走，八个数比一百个数好。
- **能让读者动手，就不要只让读者看。** 有对应组件的优先用组件：算法用 `algo`、`race`、`trace`，原理和过程用 `scene`，代码演变用 `code-steps`，能跑的例子用可运行代码块，想让读者先猜一下的用 `quiz`。一个演示讲清楚的事，正文只补一两句它没说出来的部分，不要把演示里的每一步再用文字复述一遍。
- **反例和边界比正例更有料。** 顺序打乱会怎样，差一个会怎样，数据量变成一百万会怎样。读者会问的"那如果……"，正是值得写的部分。
- **数字要算过、代码要跑过。** 复杂度、比较次数、运行结果，亲手算一遍或跑一遍再写，不要凭记忆。
- **读者可以是刚入门的人。** 科普文不受"读者是同行"那条约束，可以解释基础概念；但仍然不要摆教学姿态，不说"同学们""你学会了吗"。

### 讲一个系统、一个框架：四幕剧本

讲"X 是怎么工作的"（一个框架、一套架构、一个产品的内部），最容易写成一堆机制平铺：每页讲一个特性，观众看完不知道它们为什么放在一起。按下面四幕来排，每一幕回答一个问题，次序不要乱：

1. **问题（一两页）。** 按"背景—冲突—问题—答案"开场：先交代它所处的环境，再说那里出了什么矛盾（不这么做会怎样），由矛盾引出一个问题，最后用一句话给出 X 的答案。答案要在第一幕就说出来，后面都是在拆这句话。不要从一个具体场景、一个特性、一段代码直接开讲。
2. **一层层拆（三四页）。** 像看地图一样逐级放大：先是整体由哪几大块组成，再放大到块与块之间怎么连，再放大到一块的内部。每一层只回答一个问题，讲不到的细节不硬塞；为了讲某个机制而讲（状态机、内部字段）的页，砍掉。
3. **跟着一次请求走（三四页）。** 拿一个具体的请求，从进入系统到结果出来，按真实的先后顺序走一遍，经过哪一层就点亮哪一层。这一幕要去源码或官方文档里核对顺序和名字，不能凭推理排。
4. **收尾（一两页）。** 代价和边界，再用一句话回到第一幕的答案。

两条贯穿全篇的规矩：

- **一个例子用到底。** 第一幕里出现的那个例子（比如"用户让 Agent 跑一下测试"），拆层时还是看它，走流程时还是跟着它，观众不用每页换一个新东西。
- **每页标明"你在这里"。** 第二、三幕的画面里放一张缩小的全景，高亮当前讲到的那一层或那一步。

实验和实测是为论证服务的：先排好四幕，再看哪一步需要一个实测来证明，不要因为手上有一段跑通的实验就给它单开一页。

### 按视频的模子写

这个站的文章都可能做成演示和视频：每个二级标题是一页，这一页的 `:::notes` 是配音，场景动画每一步的 `say` 也是配音（标记写法见 `markup` 技能）。所以从动笔起就按一页一页来写，不要先写成长文再拆。

- **第一句就说这期讲什么。** 第一页的 `:::notes` 开口就点题："今天我们来聊聊，大模型是怎么……的：KV 缓存。"观众先知道这期要回答什么，再进例子。不要上来就讲一个场景、一个现象，让观众猜这是在讲什么。封面和结尾只停一秒，不靠它们交代主题。
- **文章写全，演示自动只放图形。** 同一篇文章有两种看法：读文章的人没有讲解，要能只靠文字读懂；看演示和视频的人有讲解，要的是图形。所以正文照常写完整的段落，不要为了视频把文章压成一页一句话。演示会自动挑出图形：一节里有场景、图、表、代码时，普通段落只留在文章里，演示页只放图形。某句结论想在演示里也出现，包进 `:::present`（写法见 `markup` 技能）。
- **每页的图形是一个动画。** 每页的主体是一个分步骤的 `scene`（流程用 `flow`，算法用 `algo`、`trace`），观众看着画面一步步变化就能懂。一节里只有文字的，演示里就是一张文字页，视频里就是在念 PPT，要讲的东西尽量画出来。
- **`:::present` 只包演示真正需要的那句话。** 场景动画在演示里独占一页，包进 `:::present` 的文字会单独成一张文字页，视频里配音和画面就对不上了。所以一节里最多包一两句结论，放在动画后面；动画前面的引子不要包。
- **画面讲道理，讲稿配解说。** "为什么"要画出来：谁和谁比、哪一条掉出了框、两个点怎么合成一个。场景每一步的 `say` 是解说，接着上一步往下讲，不照念画面下的那句字。`:::notes` 只写这一页的开场一两句，正文的讲解交给 `say`。
- **讲稿不要说两遍。** 一页的 `:::notes` 和紧跟着的第一步 `say` 是连着播的，不能说同一句话（"用的是本地搜索"接着又是"用的是本地搜索"）。写完把整篇讲稿按播放顺序连起来读一遍，删掉重复的。
- **每页都写 `:::notes`，每个场景的每一步都写 `say`。** 没写的地方，视频里就是一段没有声音的画面。
- **讲稿避开会读错的多音字。** 配音是机器读的，"重载""重启""行""长"这类字可能读成另一个音（"热重载"读成 zhòng zǎi）。讲稿里换成不会读错的说法：重新加载、热更新、重新启动。画面上和正文里的字照常写。
- **场景的第一帧不要是空的。** 视频里先播这一页的 `:::notes`，再进第一步。所有东西都放在 `step` 里才 `show`，开场那几秒观众看到的就是一张白纸。在第一个 `step` 之前先 `show` 这一页的起点（要问的问题、要读的笔记、要比的两样东西），第一步再接着往下演。
- **变化要让画面自己演出来。** 拖滑块、点按钮这些读者操作，视频里没有人去做。想让观众看到"换个参数结果就变了"，就写成一步，让柱子重新排序、让点移过去。
- **示意要标明。** 实测的数据可以直接画；为了说明规模编的数据（几百条笔记里排第几），场景标题或画面上写明"示意"。
- **画完要按视频的比例看一遍。** 用演示模式按 16:9 一步步翻：字有没有挤在一起、线有没有乱交叉、结论文字有没有真的出现。
- **视频里没用的整节只留在文章里。** 完整的实验代码、可运行的长代码、配置文件也算图形，会进演示。放在文末的 `:::article` 里：文章读者能看能跑，视频里不会出现一页缩得看不清的代码。这一节不要写 `:::notes`，否则演示里会剩一张只有标题的页。

## 写一篇文章

### 动笔之前

1. **查重。** `list_documents` 看站里写过什么，题目相近的几篇用 `get_document` 读一遍。不要写一篇和已有文章重复的；确实值得再写，就在开头点明和那篇的关系，并说清楚这次讲的是哪一层。
2. **搜知识块。** `search_blocks` 找这个题目已有的内容，有就直接引用。搜到状态是 `stale` 的块**不要引用**；如果你查清楚了新情况，顺手 `propose_block_update` 把它修正了。
3. **不知道的去查，查完建成带来源的事实块。** 手里没有可引用的内容时，正确的做法不是绕开那个说法，也不是凭印象写，而是去找一手资料——官方文档、规范、发布说明、源码——把关键事实建成 fact 块，来源填真实地址。一篇文章里查出来的新事实块，往往是它最值钱的部分。你记忆里的信息可能已经过期，尤其是版本号、状态、日期这类。

### 写的时候

- **读者是同行，不是初学者**（科普文例外，见上）。不解释对方显然已经知道的事，也不要摆出教学的姿态。这个领域的术语可以直接用；读者可能不熟、而站里建过概念块的词，页面会自动给出释义，不用在正文里再解释一遍。
- **开头不要铺垫。** 第一段就把读者放进具体的场景或问题里。「随着……的发展」「在当今」这类开场一律不要。
- **一篇只讲清楚一件事。** 小节标题是切分这件事的几个面，不是用来堆材料。
- **结构跟着料走，不套模板。** 不要每篇都是"背景—问题—方案—总结"。踩坑记录就按事情发生的顺序写，讲原理就按读者会冒出来的疑问排。小节标题用正文里的一句话，不用"问题分析""解决方案"这种空标题。
- **列表只给真正并列的东西用**：步骤、清单、几个选项的对比。一段推理硬拆成一串列表，读起来就是碎的。粗体一篇只留几处最关键的，不要每段都加。
- **具体压过抽象。** 能写数字就不要写「显著」，能写出错信息就不要写「报错了」，能写命令就不要写「进行相关配置」。「性能有所提升」没有信息量，「从 1.2 秒降到 0.1 秒」才有。
- **需要下判断时有两条路**：引用站长已有的观点块（`search_blocks` 里 `type` 为 `opinion` 的）；或者把判断建立在可核实的事实上——「规范把这件事写成强制条款，等于承认它容易做错」，这是从事实出发的推论，可以写。替站长表态不可以。
- **结尾落在一个判断或一个动作上。** 不要用「总之」「希望对你有帮助」收尾。
- **长度由料决定。** 一个发现、一次踩坑，三五百字讲清楚就是一篇；讲原理、拆实现的，一千到两千字。宁可短，不要为了"像一篇文章"去补背景、补延伸阅读、补"当然它也有局限"。

### 不要写出 AI 腔

这是读者一眼认出「这篇是机器写的」的地方，也是最伤文章的地方。下面每一条都要当成硬规则：

- **不要总分总。** 不要开头预告「本文将从三个方面展开」，不要结尾再把讲过的复述一遍。讲完就停。
- **不要用「首先」「其次」「最后」「综上所述」「总而言之」串段落。** 段落之间靠意思接上，不靠连接词。
- **不要堆对称句式。** 「不仅……而且……」「既……又……」「既是……也是……」连用两次以上，整篇就开始发假。
- **删掉这些词组**：值得注意的是、众所周知、不言而喻、毋庸置疑、显而易见、在当今这个……的时代、随着……的不断发展、无疑是、堪称、赋能、助力、深度赋能。
- **不要让段落一样长、小节都正好三个要点。** 真实的思考不是对称的：该一句话说完的就一句话，该展开的展开。
- **没有判断的时候不要硬下判断。** 「这无疑是一次重要的变革」这种话不增加任何信息，只暴露写的人没想清楚。
- **不要用排比抬高语气。** 「它改变了……，重塑了……，定义了……」——删掉，换成一句具体的。
- **少用感叹和反问。** 一篇文章里最多一处。
- **不要用"不是……而是……"制造转折。** 偶尔一次可以，成了习惯就是套路。
- **不要每段末尾补一句总结或金句。** 段落讲完事情就结束，不需要再替读者提炼一遍。
- **不要"让我们来看看""接下来我们"。** 直接看。

### 交稿前自查

- 把站名和项目名换掉，这篇放到别的博客还成立吗？成立，说明里面没有这个站独有的东西，回去补料，补不到就不发。科普文看例子和演示是不是自己设计的。
- 有没有哪句写成了站长的经历或看法，其实是你补的？有就删掉，或者去问站长。
- 每个事实性的说法都有依据了吗？没有依据的，要么补知识块，要么删掉。
- 有没有哪一段删掉之后，读者不会损失任何东西？有就删掉它。
- 第一句能不能直接删？能删说明它是铺垫。
- 通读一遍，把读起来不像人说话的句子改掉。

### 标题和摘要

- **标题是一个短句，直接下判断或点出要害**，不是关键词堆砌。话题需要先交代背景时，用冒号分成两段。
- 不要写「浅谈……」「……详解」「……最佳实践」「一文看懂……」这类标题。
- 拿不准调子，就用 `list_documents` 看站里已有的标题，跟着那个调子走。每个站的口气不一样，以这个站已经发过的为准。
- **摘要是列表页和搜索引擎看到的一两句话。** 要能脱离标题独立看懂，说清楚这篇解决什么问题，不要把标题换个说法重说一遍。
