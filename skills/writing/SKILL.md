# 写作与知识块整理

## 写一篇文章

### 动笔之前

1. **查重。** `list_documents` 看站里写过什么，题目相近的几篇用 `get_document` 读一遍。不要写一篇和已有文章重复的；确实值得再写，就在开头点明和那篇的关系，并说清楚这次讲的是哪一层。
2. **搜知识块。** `search_blocks` 找这个题目已有的内容，有就直接引用。搜到状态是 `stale` 的块**不要引用**；如果你查清楚了新情况，顺手 `propose_block_update` 把它修正了。
3. **不知道的去查，查完建成带来源的事实块。** 手里没有可引用的内容时，正确的做法不是绕开那个说法，也不是凭印象写，而是去找一手资料——官方文档、规范、发布说明、源码——把关键事实建成 fact 块，来源填真实地址。一篇文章里查出来的新事实块，往往是它最值钱的部分。你记忆里的信息可能已经过期，尤其是版本号、状态、日期这类。

### 写的时候

- **读者是同行，不是初学者。** 不解释对方显然已经知道的事，也不要摆出教学的姿态。这个领域的术语可以直接用；读者可能不熟、而站里建过概念块的词，页面会自动给出释义，不用在正文里再解释一遍。
- **开头不要铺垫。** 第一段就把读者放进具体的场景或问题里。「随着……的发展」「在当今」这类开场一律不要。
- **一篇只讲清楚一件事。** 小节标题是切分这件事的几个面，不是用来堆材料。
- **具体压过抽象。** 能写数字就不要写「显著」，能写出错信息就不要写「报错了」，能写命令就不要写「进行相关配置」。「性能有所提升」没有信息量，「从 1.2 秒降到 0.1 秒」才有。
- **需要下判断时有两条路**：引用站长已有的观点块（`search_blocks` 里 `type` 为 `opinion` 的）；或者把判断建立在可核实的事实上——「规范把这件事写成强制条款，等于承认它容易做错」，这是从事实出发的推论，可以写。替站长表态不可以。
- **结尾落在一个判断或一个动作上。** 不要用「总之」「希望对你有帮助」收尾。
- 长度看内容，通常一千到两千字。讲不满就写短，不要注水。

### 不要写出 AI 腔

这是读者一眼认出「这篇是机器写的」的地方，也是最伤文章的地方。下面每一条都要当成硬规则：

- **不要总分总。** 不要开头预告「本文将从三个方面展开」，不要结尾再把讲过的复述一遍。讲完就停。
- **不要用「首先」「其次」「最后」「综上所述」「总而言之」串段落。** 段落之间靠意思接上，不靠连接词。
- **不要堆对称句式。** 「不仅……而且……」「既……又……」「既是……也是……」连用两次以上，整篇就开始发假。
- **删掉这些词组**：值得注意的是、众所周知、不言而喻、毋庸置疑、显而易见、在当今这个……的时代、随着……的不断发展、无疑是、堪称、赋能、助力、深度赋能。
- **不要让段落一样长、小节都正好三个要点。** 真实的思考不是对称的：该一句话说完的就一句话，该展开的展开。
- **没有判断的时候不要硬下判断。** 「这无疑是一次重要的变革」这种话不增加任何信息，只暴露写的人没想清楚。
- **不要用排比抬高语气。** 「它改变了……，重塑了……，定义了……」——删掉，换成一句具体的。
- **少用感叹和反问。** 一篇文章里最多一处。

### 交稿前自查

- 每个事实性的说法都有依据了吗？没有依据的，要么补知识块，要么删掉。
- 有没有哪一段删掉之后，读者不会损失任何东西？有就删掉它。
- 第一句能不能直接删？能删说明它是铺垫。
- 通读一遍，把读起来不像人说话的句子改掉。

### 标题和摘要

- **标题是一个短句，直接下判断或点出要害**，不是关键词堆砌。话题需要先交代背景时，用冒号分成两段。
- 不要写「浅谈……」「……详解」「……最佳实践」「一文看懂……」这类标题。
- 拿不准调子，就用 `list_documents` 看站里已有的标题，跟着那个调子走。每个站的口气不一样，以这个站已经发过的为准。
- **摘要是列表页和搜索引擎看到的一两句话。** 要能脱离标题独立看懂，说清楚这篇解决什么问题，不要把标题换个说法重说一遍。

## 知识块

### 类型

| 类型 | 用途 | 来源要求 |
|---|---|---|
| fact | 可核实的客观说法 | 至少一个来源链接 |
| concept | 术语和定义，`data` 里要有 `term` | 可选 |
| code | 一段代码，`data` 里要有 `language` 和 `code` | 无 |
| data | 表格数据，`data` 里要有 `columns` 和 `rows` | 至少一个来源链接 |
| opinion | 站长的判断和立场 | 无，来源是站长本人 |
| experience | 站长亲手做过的事和结果 | 无，来源是站长本人 |

观点和经历只能来自站长提供的素材。不要替站长编造观点。

### 粒度规则

1. **独立变化**：如果一个块里的一半内容可能过期而另一半仍然成立，就拆成两个。
2. **独立可读**：脱离任何文章也能读懂。不用"它""上个月"这类依赖上下文的说法，日期写绝对日期。
3. **只收硬内容**：过渡、铺垫、修辞留在文章的行文里，不要做成知识块。
4. **先查后建**：`create_block` 发现相似的块时会返回它们。如果其中某个就是你要的，直接引用；确实是新内容，再带上 `confirmNew: true` 创建。

### 命名取值

事实块可以在 `data.values` 里带上容易变化的具体数值，例如 `{"values": {"version": "16.4"}}`。文章可以只取这个值，数值更新时文章自动跟随。

## 正文的标记语法

正文是 Markdown。引用知识块有三种写法：

| 写法 | 用途 |
|---|---|
| `:cite[你自己的文字]{b=编号}` | 依据。用自己的话行文，把依赖某个知识块的那段文字包起来。依赖多个块时写 `{b="编号1 编号2"}` |
| `:value{b=编号 key=名称}` | 取值。在句子里插入事实块的一个命名取值 |
| `::block{id=编号}` | 整块嵌入。原样显示知识块，适合代码、数据、概念定义。必须单独占一行 |

示例：

```markdown
:cite[Codex 从 2026 年 3 月起支持插件]{b=k7f3q2x9}，一个插件可以同时
打包技能和连接配置。

目前的最新版本是 :value{b=n5t2r8ye key=version}。

::block{id=c9d2h5ta}
```

要点：

- **系列。** 几篇文章连着讲一件事（比如"从零做一个博客"的第一、二、三篇）时，保存时给同一个 `series` 系列名。页面会按发布时间排出系列目录和上一篇、下一篇。先用 list_documents 看已有的系列名，接着写就用同一个名字，一字不差。单独成篇的文章不要硬凑系列。
- **术语不用标。** 公开、已核实的概念块（concept）就是站点的术语表：正文里第一次出现某个术语（或它的别名、括号前后的写法）时，页面自动加上虚线，读者悬停能看到定义，也会出现在站点的知识图谱（/graph）里。所以写到一个读者可能不懂、站里又还没定义过的概念时，值得先建一个概念块；概念块的 term 写读者最常见的叫法，别的叫法放进 aliases。
- 文章里每个事实性的说法都应该有 `:cite`。没有知识块支撑的说法，要么先建知识块，要么不写。
- `:cite` 的方括号里是文章自己的话，不必和知识块原文一样，但含义必须一致。
- **`:cite` 只包住承载那个说法的半句话，一般不超过三四十个字。** 不要把整段、整句连同解释一起包进去。
- **边界怎么定：** 一个知识块在一段里只需要标一次，包住最核心的那个判断或事实。同一段里接下来对它的展开、举例、细节，只要没有超出这个知识块的内容，就不用再包。换到下一段再次用到同一个知识块、而且是在陈述它（不是顺带提一句）时，再标一次。
- **文章要有自己的串联。** 过渡、解释、前后的呼应、对读者说的话，都写在标记外面。一篇好文章里，包在 `:cite` 里的文字只占一小部分。如果每一段都是一个 `:cite`，读起来就成了知识块的逐条复述，这样的稿子会被打回。

写法对比：

```markdown
不好：
:cite[我最后定的参照是 Notion 和飞书这类文档工具。落到界面上，就是白底、很淡的边框，
内容直接排在页面上，而不是一层层套进卡片里。颜色只留给标签和主按钮。]{b=z6ge7xdj}

好：
试了一圈之后，:cite[我把参照定在了 Notion 和飞书这类文档工具上]{b=z6ge7xdj}。
这类工具有个共同点：它们几乎不"设计"自己。白底，淡得快看不见的边框，内容就那么直接
排在页面上。你注意到的永远是内容，不是界面。
```

`save_document` 发现依据太长或占比太高时会返回提醒（`level` 为 `warning`）。提醒不会阻止保存，但请照着改好再提交。具体的线是：

- 单个 `:cite[...]` 里的文字超过 60 个字，会提醒"依据太长"。
- 正文满 200 字之后，被 `:cite[...]` 包住的文字超过正文的 60%，会提醒"占比太高"。

这两条是下限，不是目标。正常的文章里，一处依据通常是一个分句，全文的依据占比在两三成。

提交之后就不能再改了。提交前调用一次 `get_change_set`：它会返回变更集里每篇文档的完整内容、分类，以及一份最新的检查结果（`issues`），确认没有问题再 `submit_change_set`。
- 图片只能用媒体库里的：用 `list_media` 查看有哪些，按它给出的 `markdown` 写法插入。**不能引用外部图片的地址**，外链会失效，也把读者的访问暴露给了别的站点。
- 需要新图片时用 `upload_image` 传上去，返回的 `markdown` 可以直接写进正文。**只传你自己做出来的图**：截图、自己画的图表、自己生成的插图。
  - **不要把从网上找到的图片传上来。** 版权不清楚，这件事站长替你担责任。
  - **不要传含有私人信息的截图**：邮箱、密钥、聊天记录、后台界面里的真实数据。
  - `alt` 必须写清楚图里有什么。看不见图的读者靠它理解，搜索引擎也读它。
  - 能用正文里的组件讲清楚的，就不要配图。流程用 `:::flow`，结构和时序用 Mermaid，数据用 `:::chart`——这些是真正的文字和矢量，比截图清楚，深色模式下也不会变成一块白板。
  - 传上来的图片站长在审阅时会和文章一起看到，不合适会被删掉。你没有删除图片的权限，所以**不要反复试传**：传了没用上的图片攒到十张就不让再传了。
- 标题、摘要、网址别名、分类通过 `save_document` 的参数给出，不要写在正文里。正文不要以一级标题开头。
- 需要对比几样东西时用 Markdown 表格（第二行写 `|---|---|`）。表格的格子里不要放引用标记，依据写在表格前后的行文里。
- 代码块要写语言名（```ts、```bash），页面会按语言高亮。可以在语言后面加文件名和要读者注意的行：```ts title="src/app.ts" {2,4-6}，标题栏显示文件名，那几行会标出来。只标真正关键的一两处，不要整段都标。
- 想让读者自己动手试的 JavaScript，在语言后面加 `run`：```js run。代码下面会出现「运行」和「改一改」，读者可以改了再跑，`console.log` 的输出显示在代码下面；没有打印时显示最后一个表达式的值。代码在读者浏览器的沙箱里运行：没有网络、没有页面（没有 fetch、document），最多跑 2 秒。所以只适合不依赖外部的小例子：算法、数据处理、语言特性。只有 JavaScript 能加 run。
- 一节讲完一个容易误解的点，可以接一道 `:::quiz` 小测验（写法见 get_component）。一篇文章两三道就够了，题目要考理解，不考记忆。
- 二级、三级标题会自动生成文章目录。一篇长文用三到六个二级标题分段，标题写这一段讲什么，不要写"第一部分"。
- 每篇文章都能一键变成演示（全屏幻灯片，也能导出成视频发到视频平台）：每个二级标题是一页，单独一行的 `---` 也分页。所以二级标题下面的内容最好一屏放得下：一个要点，加一个图、一段代码演变或一个算法动画。需要讲稿时在这一页里写 `:::notes`，文章里不显示，演示和视频里当讲稿、字幕。
- 讲代码怎么一步步写出来、怎么重构时，用 `:::code-steps`：每步只改一点，讲解写这一步为什么这样改。这是做视频时最好看的形式。
- 公式用 LaTeX 写：行内的写成 `$O(n \log n)$`；单独成段的，`$$` 各占一行，公式写在中间。保存时会检查公式能不能排出来。正文里要写美元符号本身时写成 `\$`。
- 讲架构、讲交互的先后顺序时，可以用 Mermaid 画图：代码块的语言写 `mermaid`，第一行写图的类型（`flowchart LR` 流程图、`sequenceDiagram` 时序图、`classDiagram` 类图、`stateDiagram-v2` 状态图、`erDiagram` 实体关系图、`gantt` 甘特图）。简单的「谁到谁」用 `:::flow` 更好看，结构复杂、要分支和子图时再用 Mermaid。节点文字尽量短。
- 补充说明可以写成注释：正文里写 `[^1]`，文末写 `[^1]: 注释内容`。只放会打断正文的旁支信息，不要把正文该讲的东西藏进注释。
- 带动画的组件（图表、关键数字、分步讲解、流程图）是为了把一件事讲得更清楚，不是装饰。一篇文章用一两个就够了，能用一句话说清楚的不要画图。
- 讲算法和数据结构时，用 `::algo` 放一个可以播放的演示，比文字描述清楚得多。演示前用一两段话讲清楚思路，演示后指出读者该注意的地方（比如"注意基准归位之后左右两边就不再交换了"）。输入要小，排序 8 到 12 个数正合适；挑能体现算法特点的输入，比如演示快速排序最坏情况就给一个已经有序的数组。
- 内置的 `::algo` 里没有的算法，或者想演示文章里自己那种写法时，用 `:::trace` 写一段真正的 JavaScript 驱动动画：动画旁边显示的就是这段代码，和文章讲的写法完全一致。代码要短、好读，变量名和文章正文里的说法对上；compare、swap、step 的说明写成讲给读者听的话。保存时代码会实际运行一遍，出错会告诉你第几行，照着改就行。
- 标签：每篇 1 到 3 个最合适，最多 5 个。先用 `list_tags` 看已有的，意思相同的就用已有的写法，不要新起一个近义词。标签写读者会拿来找文章的词（例如 `SQLite`、`部署`），不要写"思考""总结"这种对谁都适用的词。
- 每篇文章都要归入一个分类。先用 `list_categories` 查看有哪些分类，选最贴切的一个。没有合适的分类时不要自己编，在变更集的说明里告诉站长。
- `save_document` 返回错误时不会保存。按错误信息修正后重新保存。

## 修订

知识块变化后，引用它的文章需要修订。

**你要更新一个知识块时：**

1. `open_change_set`，类型选 `block_update`。
2. `propose_block_update`，写明原因。返回的 `impact.citations` 列出了所有以依据方式引用它的文章和对应的文字。
3. 对每篇受影响的文章：`get_document` 读出正文，改写相关文字，用 `save_document` 在同一个变更集里保存。文字不需要改的，原样保存一次即可。
4. `submit_change_set`。站长会在一张卡片里看到知识块的变化和所有文章的修订。

只是修正错别字或补充来源、不改变含义时，`propose_block_update` 带上 `semanticChange: false`，不需要修订文章。不要为了省事滥用这个声明。

**待办里出现 `staleCitations` 时：**

说明知识块已经变化，而文章还没跟上。开一个 `document_edit` 类型的变更集，按上面第 3 步修订，然后提交。

**发现某条事实可能不成立，但还没查到新的内容时：**

先调用 `mark_block_stale` 并写明原因（哪里可能不成立、依据是什么），引用它的文章会被标出并进入待办。查清楚之后再按上面的流程更新。

**待办里的 `staleCitationsBeingRevised`：**

这些文档已经有修订在等站长的结论，不需要再处理。
