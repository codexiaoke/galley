# Galley 设计：知识块、引用与变更集

> 状态：设计稿，2026-11-12
> 前置文档：[需求文档](requirements.md)

本文档定义 Galley 的地基：知识块怎么存、文章怎么引用知识块、改动怎么审、变更怎么传播。

---

## 1. 设计目标

| 目标 | 含义 |
|---|---|
| 行文自然 | 文章读起来是连贯的文字，不是事实条目的拼接 |
| 引用不断 | 文章反复修改后，它依赖哪些知识块仍然清楚 |
| 已发布内容稳定 | 线上内容只在站长批准后才变化 |
| 变更可追踪 | 一个知识块变了，能准确找到所有受影响的位置 |
| Agent 写得出来 | 语法简单，写错了能得到明确的错误提示 |
| 审阅省力 | 一次相关的改动只审一次 |

---

## 2. 总体模型

系统里有三类东西和一个审阅单位：

| 概念 | 说明 |
|---|---|
| 知识块 | 一条可以独立核实、独立变化的硬内容 |
| 文档 | 文章和页面，正文是 Markdown 加扩展标记 |
| 引用 | 文档正文中指向知识块的标记，由程序解析后单独存表 |
| 变更集 | 一次提交审阅的全部改动，对应看板上的一张卡片 |

知识块和文档都采用"实体加版本"的结构：实体本身只记录身份和当前生效的版本，每次修改产生一个新版本，旧版本永久保留。

---

## 3. 知识块

### 3.1 通用字段

| 字段 | 说明 |
|---|---|
| 编号 | 8 位随机字符，例如 `k7f3q2x9`，永不重复使用 |
| 类型 | 事实、概念、代码、数据、观点、经历 |
| 标题 | 一句话标签，用于搜索结果和后台列表 |
| 正文 | 简短的 Markdown |
| 标签 | 与文章共用一套标签 |
| 可见性 | 公开或私密 |
| 状态 | 见 3.3 |
| 来源素材 | 如果由素材箱里的某条素材整理而来，记录是哪一条 |
| 作者 | 哪个 Agent 或站长 |

编号使用随机字符而不是有含义的短名。原因：Agent 可能凭印象编造一个看起来合理的短名并碰巧撞上另一个知识块；随机编号编造不出来，写错了一定会被校验发现。

### 3.2 各类型的专有字段

| 类型 | 专有字段 |
|---|---|
| 事实 | 陈述；来源列表（链接、标题、支持该陈述的原文摘录、访问日期）；事实成立的日期；建议复查日期；可选的命名取值 |
| 概念 | 术语；别名；定义；可选的来源 |
| 代码 | 语言；代码；说明 |
| 数据 | 表格或序列；单位；来源；数据日期 |
| 观点 | 陈述；理由；形成日期 |
| 经历 | 做了什么；时间和背景；结果 |

"命名取值"是事实块里可以单独取用的值，例如一条关于某软件最新版本的事实，可以带一个名为 `version` 的取值。文章可以只取这个值，见 4.1。

### 3.3 状态

| 状态 | 含义 |
|---|---|
| 待核实 | Agent 新建，站长还没批准 |
| 已核实 | 站长批准过。对观点和经历来说，含义是"这确实是我的看法和经历" |
| 已过期 | 被标记为可能不再成立，等待更新 |
| 已停用 | 不再使用，保留历史 |

### 3.4 粒度规则

写进"知识块整理"技能，由 Agent 执行：

1. **独立变化测试**：如果一个块里的一半内容可能过期而另一半仍然成立，就应该拆开。
2. **独立可读**：脱离任何文章也能读懂。不用"它""上个月"这类依赖上下文的说法，日期写绝对日期。
3. **只收硬内容**：事实、定义、代码、数据、站长的观点和经历。过渡、铺垫、修辞留在行文里。
4. **先查后建**：新建前先搜索，已有相同内容的块就直接引用。

## 4. 引用

### 4.1 三种引用方式

核心决定：**引用分为"依据"和"嵌入"两大类**，因为它们在知识块变化时的处理方式完全不同。

| 方式 | 写法 | 效果 | 知识块变化时 |
|---|---|---|---|
| 依据 | 行文自由书写，把依赖某个知识块的那段文字标出来 | 文字是文章自己的，读者看到的是自然的句子 | 文字需要 Agent 重写，站长审阅 |
| 整块嵌入 | 在文中放一个标记，原样显示知识块内容 | 代码、数据图表、定义框等 | 自动跟随，不需要重写 |
| 取值嵌入 | 在句子里插入知识块的某个命名取值 | 版本号、价格、日期等 | 自动跟随，不需要重写 |

事实、观点、经历通常用"依据"；代码、数据、概念通常用"整块嵌入"；容易变的具体数值用"取值嵌入"。

### 4.2 语法

使用 Markdown 的通用指令语法，由 remark-directive 解析。

```markdown
:cite[Codex 从 2026 年 3 月起支持插件]{b=k7f3q2x9}，一个插件可以同时
打包技能和 MCP 连接配置。

我的看法是，:cite[技能应该放在服务端，而不是每个 Agent 各存一份]{b=p4m8w1zc}。

目前的最新版本是 :value{b=n5t2r8ye key=version}。

::block{id=c9d2h5ta}

::chart{data=d81k2mvv type=bar title="各系统支持 MCP 的时间"}

:::callout{type=warning}
这里是提示框的内容，里面仍然可以使用 :cite[依据标记]{b=k7f3q2x9}。
:::
```

| 标记 | 含义 |
|---|---|
| `:cite[文字]{b=编号}` | 依据。方括号里是文章自己的文字。依赖多个块时写 `{b="编号1 编号2"}` |
| `:value{b=编号 key=名称}` | 取值嵌入 |
| `::block{id=编号}` | 整块嵌入，按知识块的类型显示 |
| `::组件名{参数}` | 单行组件。需要数据的组件用 `data=编号` 指向数据块，算作整块嵌入 |
| `:::组件名{参数}` 到 `:::` | 可以包含内容的组件 |

规则：

- 正文里只写知识块编号，不写版本。版本由程序在保存时记录。
- 标题、摘要、标签、封面、网址别名是结构化字段，不写在正文里。
- 文章和页面使用同一种格式。页面只是更多地使用布局类组件。
- 只有已登记的标记名才按指令处理，其余情况还原成普通文字，避免正文里的冒号被误判。

### 4.3 保存时的解析与校验

每次保存文档版本时，程序解析正文并做以下检查，错误信息返回给 Agent：

| 检查 | 错误示例 |
|---|---|
| 知识块存在 | "第 3 段引用的 k7f3q2x8 不存在。相近的编号：k7f3q2x9" |
| 引用方式与类型匹配 | "c9d2h5ta 是代码块，不能用于 chart 的 data 参数" |
| 取值存在 | "n5t2r8ye 没有名为 price 的取值，可用的有：version" |
| 组件参数合法 | "chart 的 type 只能是 bar、line、pie" |
| 知识块状态 | 警告："p4m8w1zc 已过期，建议先更新它" |

解析出的引用存入引用表，每条记录：所属文档版本、知识块编号、引用方式、依据文字、在文中的顺序。

### 4.4 版本锁定

| 引用方式 | 是否锁定版本 | 原因 |
|---|---|---|
| 依据 | 锁定到写作时该知识块的版本 | 这段文字是针对那个版本写的，版本变了文字可能就不对了 |
| 整块嵌入、取值嵌入 | 不锁定，始终显示当前生效的版本 | 内容原样来自知识块，自动跟随才有意义 |

由此得到过期的判定，不需要额外存标志：

> 一条依据引用过期，当且仅当它锁定的版本不是该知识块当前生效的版本，或者该知识块的状态是已过期或已停用。

### 4.5 前台呈现

原则：**阅读时不显示系统信息。** 知识块的编号、内部标题、核实日期、版本号、是否过期，都是系统运转用的信息，读者不需要看到。

- 依据文字带一个不显眼的点状下划线。读者把鼠标移上去（触屏上点一下）才出现悬浮卡片，里面只有这条依据的内容和来源链接。
- 悬浮卡片出现在整句话的正下方、鼠标附近，始终留在正文栏和窗口之内，不遮挡这句话本身。
- 嵌入的代码块和正文里普通的代码块外观相同。数据和图表只显示作者写的标题和数据来源。
- 文章页只显示发布日期；文章修订过时加上"更新于某日"，点开是这篇文章的修改记录（每次上线的日期、改动说明、改了哪些字）。不显示版本号和知识块数量。
- 公开、已核实的概念块是站点的术语表：正文里每个术语第一次出现时带一条朱红色的细虚线，悬停看定义，和依据的灰色点线区分开。概念、文章和它们之间的联系（引用、提到、链接）合成一张知识图谱，在 /graph。
- 知识块过期、等待修订这类状态只在后台显示。后台的审阅预览会额外标出每个知识块的编号、内部标题、核实日期和过期状态。

## 5. 版本与变更集

### 5.1 变更集

变更集是审阅的唯一单位，对应看板上的一张卡片。它包含一组新版本，这些版本要么一起生效，要么都不生效。

| 变更集类型 | 典型内容 |
|---|---|
| 新文章 | 一个文档版本，加上为它新建的若干知识块 |
| 文章修改 | 一个文档的新版本 |
| 页面调整 | 一个页面的新版本 |
| 知识整理 | 从素材整理出的一批新知识块 |
| 知识更新 | 一个知识块的新版本，加上所有受影响文档的新版本 |

状态：进行中、待审、已批准、已打回、已撤回。

### 5.2 规则

1. **Agent 的一切修改都发生在某个变更集里。** Agent 先开启一个变更集，在里面创建和修改内容，最后提交审阅。
2. **批准是原子的。** 站长批准后，变更集里的所有版本在同一个事务里生效。
3. **结论针对整张卡片。** 第一版只有"批准"和"打回"两种，不做逐项批准。站长对其中某一项不满意时，可以写批注后打回，也可以自己直接改完再批准。
4. **同一个对象同时只能在一个未结束的变更集里。** 一个文档或知识块已经在某个待审的变更集中时，其他变更集不能再修改它。这样不需要处理合并冲突。
5. **站长直接修改立即生效。** 站长是最终把关人，在后台的修改不经过审阅，但同样产生版本记录。
6. **回滚以变更集为单位。** 撤销一张已批准的卡片，就是把其中所有对象恢复到之前的版本。

## 6. 变更传播

### 6.1 Agent 更新一个知识块

1. Agent 提议更新知识块，说明原因和新来源。程序开启一个"知识更新"变更集。
2. 程序返回影响清单：
   - 哪些文档以"依据"方式引用了它，每处的依据文字是什么。
   - 哪些文档以"嵌入"方式引用了它（这些会自动跟随，仅供知悉）。
3. Agent 逐处处理依据引用，二选一：
   - 重写那段文字，产生该文档的新版本，放进同一个变更集。
   - 确认文字不需要改，只更新锁定的版本。
4. Agent 提交审阅。
5. 站长看到一张卡片：顶部是知识块的前后对比，下面是每篇受影响文档的改动，以及会自动跟随的嵌入位置的预览。
6. 批准后，知识块和所有文档的新版本同时生效，相关页面的缓存刷新。

### 6.2 不影响含义的修改

修正错别字、补充一个来源这类修改，不应该让所有引用它的文章都重审。

提议更新时可以声明"不改变含义"。这种版本生效后，原有的依据引用自动改为锁定新版本，不产生修订任务。站长在审阅卡片上能看到这个声明，认为不妥可以打回。

### 6.3 站长直接修改知识块

修改立即生效。锁定旧版本的依据引用变成过期状态，线上文章暂时保持原文。Agent 下次运行时在待办里看到修订任务，按 6.1 的第 3 步起处理，提交一个变更集给站长审。

### 6.4 标记过期

站长或 Agent 发现某条事实可能不成立，但还没有新内容时，可以先把知识块标记为已过期。效果：

- 后台的看板和审阅预览里标出引用它的位置。前台不向读者提示（见 4.5）。
- Agent 的待办里出现"核查并更新这个知识块"的任务。

### 6.5 应对审阅疲劳

- 一个知识块引起的所有改动合并在一张卡片里。
- 不改变含义的修改不产生修订。
- 嵌入类引用不需要重写，卡片里只做预览。
- 审阅界面默认只展开有文字改动的位置。

## 7. 审阅批注

- 批注针对变更集里某个具体版本的某段文字。
- 定位方式：记录被批注的原文，加上它前后的少量文字。不依赖行号或字符位置。
- 批注不跨版本迁移。Agent 提交新版本后，旧批注留在旧版本上，界面以"上一版的批注加本版的改动"的方式对照显示。
- Agent 处理每条批注时写一句回复并标记为已处理。站长可以重新打开。

依据标记本身就写在正文里，会随文字一起移动，所以引用关系不受修改影响。

## 8. 私密内容

| 规则 | 实现 |
|---|---|
| 私密块不能出现在公开内容里 | 文档正文中任何方式引用了私密块，变更集就无法被批准，程序强制检查 |
| 提示可能的间接泄露 | 程序记录 Agent 在一个变更集进行期间读取过哪些私密块，在审阅卡片上列出，提醒站长留意是否被换了说法写进正文 |
| 私密块改为公开 | 只有站长能操作 |

第二条不能阻止泄露，只是把风险摆到站长面前。

---

## 9. 站内记忆与查重

- 知识块的标题、正文、术语建立全文索引。
- Agent 写作前搜索知识库，了解站里已经确认了什么。
- 新建知识块时，程序用全文搜索找出相似的已有块并返回。Agent 需要明确表示"确实是新内容"才能继续创建。
- 搜索结果包含每个块被引用的次数，帮助 Agent 判断哪些是站里的核心内容。

## 10. 数据表

只列与本设计相关的核心表。

| 表 | 主要字段 |
|---|---|
| 知识块 | 编号、类型、可见性、状态、当前版本、来源素材、作者、创建时间 |
| 知识块版本 | 所属知识块、版本号、标题、正文、专有字段、来源、成立日期、复查日期、是否改变含义、作者、所属变更集、状态 |
| 文档 | 编号、种类（文章或页面）、网址别名、状态、当前版本、发布时间 |
| 文档版本 | 所属文档、版本号、标题、摘要、正文、其他字段、作者、所属变更集、状态 |
| 引用 | 所属文档版本、知识块、引用方式、锁定的知识块版本、顺序、依据文字、参数 |
| 变更集 | 类型、标题、说明、状态、关联选题、触发原因、创建者、提交时间、结论时间 |
| 审阅批注 | 所属变更集、目标版本、定位信息、内容、作者、状态、回复 |
| 私密读取记录 | 变更集、知识块、Agent、时间 |
| 知识块全文索引 | 标题、正文、术语 |

文档的"种类"字段留有扩展余地，第二版的短笔记可以作为新的种类加入。

## 12. 取舍记录

| 没有采用的方案 | 原因 |
|---|---|
| 只用嵌入，文章完全由知识块拼接 | 行文生硬，读起来像条目列表 |
| 只用依据，不做嵌入 | 代码和数据复制到每篇文章里，更新时每处都要重写 |
| 用脚注式写法标注来源 | 脚注只能标出一个点，不能标出"哪段文字"依赖这个知识块，审阅时无法高亮，修订时 Agent 不知道该改哪里 |
| 用有含义的短名做编号 | Agent 可能编造出碰巧存在的短名 |
| 正文里写明引用的版本 | 增加 Agent 的负担，容易写错；由程序记录更可靠 |
| 知识块更新后自动改写文章并直接生效 | 线上内容未经站长批准就变化，违反"发布由人把关" |
| 逐项批准 | 第一版增加大量界面和状态复杂度，整张卡片批准加站长直接修改已经够用 |
| 多个变更集同时修改同一对象 | 需要合并冲突的机制，单人站点不值得 |

## 13. 需要在真实写作中验证的事

| 问题 | 验证方式 |
|---|---|
| 粒度规则是否合用 | 用它整理十篇真实文章，看知识块的复用率和数量 |
| 依据标记是否影响 Agent 的行文质量 | 已验证（Codex）：只说"每个说法都要有依据"时，它会把整段包进标记，文章变成逐条复述。在技能里写明"只包住半句话、文章要有自己的串联"并给出正反例之后，行文正常 |
| 一篇文章里标记的密度多少合适 | 观察审阅时的阅读体验 |
| "不改变含义"的声明是否会被 Agent 滥用 | 统计该声明被站长打回的比例 |
| 相似块提示是否足以防止重复 | 定期检查知识库里的重复内容 |
